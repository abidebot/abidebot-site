For developers

munu: the language AbideBot is written in.

munu is a programming language for programs that have to keep running and be checked before they do. Functions are finite (mu) or ongoing (nu). Programs are contracts that carry their own recovery rules and deadlines. Shared state is single-assignment dataflow over psi-terms, and the network that will carry it is designed around hyperbolic routing. Everything on this page is a real excerpt from munu’s source and compiler tests, except seven examples written for this page and labelled as such, and anything that says planned.

How the three parts of AbideBot fit around munu.

mu and nu

Shaped for the model that writes it.

munu is designed to be written mostly by an AI agent and read by people. The syntax is built for that: finite and ongoing functions are told apart up front, functions are tables of cases, and rules come before the body.

Runs
mu add(total: i64, n: i64) -> i64 {
    total, n => total + n
}

mu tally() -> i64 {
    _ => {
        let s1 = add(0, 2);
        let s2 = add(s1, 3);
        add(s2, 4)
    }
}
No mutation

State is passed along, not changed

add takes the running total and returns the next one, and changes nothing. tally hands each result to the following call by name, so s1 and s2 are new values rather than one variable written over. munu has no mutable variables, loops or compound assignment, so nothing shifts underneath the code: every step’s input and output are on its own line.

A function is a table

Cases on the left, results on the right

Each case gives one pattern per input, read left to right like the columns of a table, with its result on the right. Calling the function means finding the case whose patterns fit the inputs and returning the result beside it. That is the shape of attention in a transformer, which compares a query against keys and returns the values paired with the closest matches. The construct munu code is built from is the operation the model is built around.

Runs
struct Item { sku: string, qty: i64 }
enum Msg { Buy { item: Item }, Ping }

mu headline(inbox: [Msg]) -> string {
    [Msg::Buy { item: Item { sku: "tea", qty: 1 } } | _] => "1 tea",
    [Msg::Buy { item: Item { sku, .. } } | _] => sku,
    _ => "nothing"
}

Deep patterns

One case can look several layers down

Patterns nest. The first case looks into the list, through its first message, into the item that message carries and down to the item’s fields, testing exact values on the way; the second binds the name sku three levels down and skips the rest with ... Because destructuring happens on the left, the result on the right uses those names directly, with no field accesses or chain of conditions, and each case can be as specific a key as it needs to be.

Runs
mu is_empty(list: [i64]) -> bool {
    [] => true,
    [_ | _] => false
}

nu count_from(n: i64) -> [i64] {
    n => [n | count_from(n + 1)]
}

Finite or ongoing

Finishing or never-ending, declared up front

mu marks a function that must finish: here each case gives its answer at once. nu marks one that never finishes but must keep producing: every step hands back another element before it carries on. Because the keyword comes first, the kind of function is settled before a single case is written.

Runs
enum Size { Small, Large }
struct Cup { size: Size, price: i64 }

mu first_price(cups: [Cup]) -> i64 {
    [] => 0,
    [head | _] => match head.size {
        Size::Small => head.price,
        Size::Large => head.price + 1
    }
}

Familiar forms

Written the way common code is written

Enums, structs, typed fields, braces and a match look the way they do in widely used languages, and the list pattern [head | _] follows a long-standing convention. In our measurements 50 of the 54 keywords are single tokens in widely used tokenizers.

Rules before the body

Requirements, guarantees and the stopping rule come first

What the input must satisfy, what the result promises and why the recursion ends are written before the body, in a fixed order. Writing left to right, a model has read every constraint before it writes the first case.

Runs
struct Account { owner: string, balance: i64 }

mu deposit(a: Account, n: i64) -> Account {
    a, n => Account { balance: a.balance + n, ..a }
}
+1 hidden line

Immutable values

A value is copied with changes, not edited

deposit leaves the account it is given alone. It builds a new Account with the balance replaced, and ..a fills in every other field from the original. This is a functional update: nothing is edited in place, so any part of the program still holding the original sees exactly the balance it had before.

Every case is covered

A missing case is a compile error

This is from a compiler test. The None case has no row, so the program is rejected as a non-exhaustive match. With no loop, return, break or try keywords either, every path a function can take is one of its listed cases.

Not in the compiler yet
mu one_thing() -> i64 {
    _ => {
        type P;
        let x;
        let y: P;
        x: P;
        x = y;
        P = i64;
        y = 42;
        x

Bind, not assign

A name can be declared with its type and no value

P is a type nobody has fixed yet. x starts with no type and no value, and y with type P and no value; x: P puts x under the same unknown type, and x = y, with both still empty, copies nothing and makes the two names one variable. P = i64 then fixes the type for both, and y = 42 gives that one variable its value, so x reads 42 and anything waiting on x is woken by the bind on y. Every = in munu is a bind, whether it joins two variables, joins two types or gives one a value, and once two things are joined they stay one thing.

Lazy computation

Work happens only when its result is needed

Laziness belongs to the function. It is written once, where the function is declared, and never at the call. A plain mu is eager, so first does its work as soon as it is called. cube is declared lazy mu: calling it only makes the variable its result will be bound to, and the body runs when something reads that variable. Nothing reads c, so cube never multiplies at all. A nu is lazy unless it is declared eager nu: count_from stands for every number from 1 upward, but first reads only the head, so one element is produced and no more. only_what_is_read gives 1, and the work nobody asked for is never done.

    _ => {

Concurrency

Spawned work meets in a variable

spawn hands back the variable a call’s result will be bound to: a and b for the squares, and the stream s for count_from. That variable is the unit of concurrency in munu. Work goes on independently until something reads a variable that is not yet bound, and only there does it wait. When each call runs is not up to spawn: the function itself settles that, as in the row above. Every variable is bound once, so side_by_side gives 35, that is 9 + 16 + 10, however the work is scheduled. A contract is spawned the same way into a named position, written let self.pos = spawn C(args);, where its supervisor restarts it from the arguments it was first given.

The honest picture: most functions in munu’s source have a single case, and multi-case tables like those above are the minority. The short examples on this page (passed-along state, the table, deep patterns, mu and nu, familiar forms, a copied value, the joined names, the lazy calls and the spawned squares) are written for it; the others are from munu’s source. The likeness to attention is one of shape only: munu does not compile to attention. Effects such as receiving a message happen through calls, not through syntax. In our own tests the language is not more compact than mainstream languages. Its advantage is structure, not size.

Contracts and supervision

Recovery is part of the program.

A contract is munu’s unit of work, supervision and security. How it recovers and how fast it must answer are written as mu-calculus formulas and constants in the code, and the compiler turns them into checks.

Type-checks
formula permanent() {
    nu X. [fail(self, _)] <restart(self)> X and [_] X
}

Supervision strategy

How a bot recovers is written down, not configured

The recovery rule is a mu-calculus formula: on any failure, restart, and keep doing that for as long as the component runs. Each component names its rule in its header (do: is what it does, must: is what it is held to), and the compiler turns the formula into a state machine at build time.

Type-checks
enum Failure { Lost }
enum Report { ChildFailed(u64, u64), ChildDone(u64) }
const REPORTS_BOUND = 8u64;
cdf RESPONSE {
    dmax: 200ms,
    handup: 50ms,
    expected: [(10ms, 0.9), (50ms, 0.99), (200ms, 1.0)]
}

eager nu drill(x: u64) -> [u64] {
    0u64 => crash Failure::Lost,
    x => [x | drill(x)]
}

pub contract Corporal(x: u64) -> [u64]
    substrate { bytecode }
{ drill(x) }

eager nu command(rs: [Report]) -> [u64] {
    [r | rest] => match r {
        Report::ChildFailed(slot, reason) => [slot | command(rest)]
    },
    [] => []
}

pub contract Major(a: u64, b: u64) -> [u64]
    substrate { bytecode }
    behaviour {
        do: nu X. [fail(alpha, Failure::Lost)] <restart(alpha)> X
                  and [done(alpha)] <absorb(alpha)> X
                  and [fail(bravo, _)] <restart(self)> X
                  and [_] X
        must: nu X. [fail(!self, _)]~deadline(RESPONSE) X
    }
    children { alpha: Corporal, bravo: Corporal }
    ports {
        reports: [Report] {
            ends: r1
            bound: REPORTS_BOUND
            do: nu X. [_] X
            must: true
        }
    }
{
    let self.alpha = spawn Corporal(a);
    let self.bravo = spawn Corporal(b);
    command(reports)
}

Supervision tree

A major runs two corporals and answers each one differently

A contract’s body can start other contracts. Major declares two positions under children and spawns a Corporal into each, alpha from a and bravo from b. Then it hands over to command, which reads the reports the kernel files on the reports port when a child fails or finishes. The major supervises both corporals, and a corporal’s failure is answered by the major’s rules, one line per case. If alpha fails with Failure::Lost, only alpha is restarted, from the argument it was first given. If bravo fails for any reason, the whole major restarts, so both corporals start again from a and b. A corporal that finishes is absorbed. The must: line holds the major to the timing in RESPONSE, a distribution rather than a single number: 90% of its answers to a child’s failure within 10ms, 99% within 50ms, and every one within 200ms, the hard limit. Spawning a corporal only binds its position. When its work runs is settled by drill, an eager nu, not by spawn. The compiler also checks the other side: an answer to a failure a child can never raise is refused at compile time. Written for this page, following the shapes in the compiler’s own tests.

Typed failures

A failure has a name and a type

Failures are declared like any other type and raised with crash. The reason travels to the supervisor, which is what lets recovery rules match on the cause instead of on a log line.

Ports

The only place order can vary.

Every other value in munu has a single writer. Where several senders must feed one stream, you declare a port and say which orders it accepts.

Excerpt
readings: [Reading] {
    ends: ctl, lhs, rhs
    bound: READINGS_BOUND
    do:
        [from(lhs)] false
        and [from(rhs)] false
        and [from(ctl)] nu X. [_] X
    must:
        <from(ctl)>~deadline(CONFIG_MUST) true
        and nu X. [_]~deadline(SAMPLE_MUST) X
}
Ports

The one declared place where order can vary

A port is where several senders feed one stream. It names its ends, a bound on how many values can wait, and a formula for the orders it accepts: here neither sensor may speak until the controller has, after which anything goes, within the stated deadlines. Every other value in the language has a single writer, so the system is designed so that run-to-run variation can enter only through ports like this one, and everything else can be reproduced.

Psi-terms

Shared work, filled in by many.

munu’s types are psi-terms: structures that can be partly known. Each party adds what it knows, and the store checks it against what everyone else said.

Psi-terms

Shared work that several parties fill in

Types are psi-terms: structures that can be partly known. A record can be built with a blank field (let y;), and each part of the program that uses it adds what it knows about that field, checked against what the others said. In the first compiler test one call expects a number and the other a true-or-false value, so the program is refused. In the second, a later assignment fills the blank. This is designed for bots collaborating on shared work: each adds what it knows, and a conflict is caught instead of overwritten.

Dataflow and scenes

Variables that are filled once, and screens that are data.

A munu variable starts empty, is filled in once and is never changed. Anything that needs it waits until it has a value. Apps use the same rule for input, and draw themselves as scene values.

Scenes

A screen is a value

An app draws itself by returning a scene: a tree of layout, text and controls built by ordinary mu functions. Nothing is painted until munuScene reads the tree. Because the screen is data, munuScene is designed to hand the same tree to the agent, which can read it and act on it without a screenshot.

Excerpt
eager nu click_cycle(n: u64) -> [SceneNode] {
    n => {
        let click;
        let label = if n == 0u64 { "Click me" } else { "Clicked!" };
        let scene = pad(40.0, 40.0, 40.0, 40.0,
            click_surface(click, button_face(label)));
        [scene | wait_click(n, click)]
    }
}
Dataflow

Wait for a value to be bound

let click; declares a variable with no value yet. The button is wired to it, and pressing it fills it in, once. The stream returns the current scene and then hands the variable to the next step, which continues only when the variable has a value. There are no callbacks or handlers to register: a party that needs a fact waits on its variable, and a party that knows it binds it.

From a test program in munu’s source. munuScene, the browser, is in development, and the agent reading scenes and binding their variables is designed, not shipped.

Hyperbolic routing

A network with no central directory.

The routing code is written in munu and exists today. The global network that will use it, connecting every munuOS machine and every bot by its QR code with end-to-end encryption, is planned.

Excerpt
mu hyperbolic_distance(r1: f64, a1: f64, r2: f64, a2: f64) -> f64 {
    r1, a1, r2, a2 => {
        let x1 = f64_mul(r1, f64_cos(a1));
        let y1 = f64_mul(r1, f64_sin(a1));
        let x2 = f64_mul(r2, f64_cos(a2));
        let y2 = f64_mul(r2, f64_sin(a2));
        let dx = f64_sub(x1, x2);
        let dy = f64_sub(y1, y2);
        let delta_sq = f64_add(f64_mul(dx, dx), f64_mul(dy, dy));
        let d1sq = f64_sub(1.0, f64_mul(r1, r1));
        let d2sq = f64_sub(1.0, f64_mul(r2, r2));
        let denom = f64_mul(d1sq, d2sq);
        f64_acosh(f64_add(1.0, f64_div(f64_mul(2.0, delta_sq), denom)))
    }
}
Hyperbolic routing

Every node has a place on a curved map

Each node is given coordinates in the Poincaré disk, a model of hyperbolic space, and this function measures the distance between two of them. A packet goes to whichever neighbour is closest to its destination, so a node needs to know only its neighbours, not the whole network. Hyperbolic space has room for very large trees with short paths, which is why it is used for routing.

Architecture

Three parts, one language.

How AbideBot is put together around munu. Parts marked planned or in development are designs, not shipped software.

munuOS In development

The always-on operating system the agent lives in: a minimal Linux-based operating system image where munu is the first process, one per customer. It includes the munu compiler. It is designed so the agent writes a module, compiles it on munuOS and swaps it in, with supervision restarting a failed part by its rule and a bad version rolling back.

munuScene In development

The AI-native browser and desktop app. It draws scenes, not HTML, and turns what you press and type into values bound to the variables the app is waiting on. The agent runs on munuOS, not in munuScene, and is designed to use the same scenes as you do.

The network Planned

Shared state as psi-terms in one store, designed so tells commute and only the new part of a value travels. Routed by hyperbolic coordinates and encrypted end to end. Sites, documents and apps are designed to live here, not on the public web.

The honest picture: the compiler, the code shown above and munuOS’s first stages exist. The agent’s direct use of apps in munuScene, the network, self-hosting and published docs are planned. We will not claim savings or uptime before we can measure them.
