For developers

munu: the language AbideBot is written in.

munu is a programming language for programs that have to keep running and be checked before they do. Functions are finite (mu) or ongoing (nu). Programs are contracts that carry their own recovery rules and deadlines. Shared state is single-assignment dataflow over ψ-terms, and the network that carries it is in development, built on hyperbolic routing and encrypted frames. Everything on this page is a real excerpt from munu’s source and compiler tests, except seven examples written for this page and labelled as such, and anything that says planned.

mu and nu

Shaped for the model that writes it.

munu is designed to be written mostly by an AI agent and read by people, and its syntax is shaped around how a transformer works: it matches queries to keys, continues regular shapes token by token, and uses only the text in its context window. Each example says what its code does and which of those it fits.

Runs
mu add(total: i64, n: i64) -> i64 {
    total, n => total + n
}

mu tally() -> i64 {
    _ => {
        let s1 = add(0, 2);
        let s2 = add(s1, 3);
        add(s2, 4)
    }
}
No mutation

State is passed along, not changed

tally never changes a value: add takes the running total and returns the next one, and each result is handed on by name, s1 into the call that makes s2. A transformer can only use the text in front of it, and here that text is everything a step depends on: add(s1, 3) names its whole input, with no field changed somewhere else for the model to keep track of. So each call can be written or checked from the tokens right beside it.

A function is a table

Cases on the left, results on the right

Each row of can_go is a pattern on the left and a result on the right, and the first row that fits is taken. That is the shape of attention, the core step of a transformer, which matches a query against keys to pick out their values: here the inputs are the query, each pattern is a key and each result is its value. Every row is short and repeats the shape of the one above, so the model writes and checks it from the tokens on that line, and the compiler rejects a missing row or one that can never match.

Deep patterns

One case can look several layers down

headline reads the first message of an inbox: a Buy of one tea gives "1 tea", any other Buy gives its sku, bound three levels down with the rest skipped by .., and anything else gives "nothing". Each pattern repeats the shape of the types declared just above it, Msg and Item, so the model writes it by copying a shape that is already in its context. The result then uses sku directly, with no chain of field accesses that could name the wrong field.

Finite or ongoing

Finishing or never-ending, declared up front

mu marks a function that must finish, like is_empty, which answers at once; nu marks one that never finishes but must keep producing, like count_from, which hands back another element before it carries on. The keyword is the first token of the declaration and a model generates left to right, so everything it writes after it is conditioned on the kind of function it has already committed to. The kind is never left for the body to reveal.

Familiar forms

Written the way common code is written

first_price returns the first cup’s price, plus one if the cup is Large, and 0 for an empty list. Enums, structs, braces and match are written as they are in widely used languages, and the list pattern [head | _] follows a long-standing convention, so much of this is a shape the model has seen many times and can continue token by token. In our measurements 50 of the 54 keywords are single tokens in widely used tokenizers, so the keywords mostly reach the model whole.

mu ring_truncate(list: [Histogram], k: i64) -> [Histogram]
  requires (k >= 0i64)
  ensures (r) hist_list_len(r) <= k
  decreases list
{
    [], _ => [],
    [_ | _], 0i64 => [],

Rules before the body

Requirements, guarantees and the stopping rule come first

ring_truncate states what its input must satisfy (requires), what the result promises (ensures) and why the recursion ends (decreases), and only then gives its three cases. A model writes left to right, so by the first case every constraint is already in its context and each token of the body is generated with them in view. The order is fixed, so each kind of rule is always found in the same place.

Immutable values

A value is copied with changes, not edited

deposit returns a new Account with the balance replaced, and ..a fills in every other field from the original, which is left as it was. A model works out what a name holds by attending back to the text that made it. Since nothing is edited in place, that text stays true for the rest of the program, so what the model read for a earlier is still what a is where it is used.

Every case is covered

A missing case is a compile error

This is from a compiler test. handle has a row for Click but none for None, so the program is rejected as a non-exhaustive match, and the error names the case that is missing. That message is text the model can act on at once by adding the row, where a failure found only at run time would leave nothing to read.

Runs
mu one_thing() -> i64 {
    _ => {
        type P;
        let x;
        let y: P;
        x: P;
        x = y;
        P = i64;
        y = 42;
        x
    }
}
Bind, not assign

A name can be declared with its type and no value

x and y start with no value, and x = y joins them into one variable before either has one; P = i64 then fixes their shared type, and y = 42 gives that one variable its value, so x reads 42. Every = in munu is a bind, and once two things are joined they stay one thing. A model goes only by the text, so what x is gets answered by the lines that bind it, not by working out when each line ran.

Runs
mu add(a: i64, b: i64) -> i64 {
    a, b => a + b
}

mu square(n: i64) -> i64 {
    n => n * n
}

mu meet() -> i64 {
    _ => {
        let x;
        let y;
        let total = spawn add(x, y);
        x = spawn square(3);
        y = spawn square(4);
        total
    }
}
Concurrency

Spawned work meets in a variable

meet declares x and y with no value, spawns add(x, y) before either has one, and only then binds them to square(3) and square(4), so total is 9 + 16 = 25. The variable is the unit of concurrency: spawn hands back the variable a result will be bound to and has no say over when a call runs, which the function’s declaration settles; add waits only where it reads x or y while they are unbound, and every variable is bound once, so the answer is the same in any order. Move the let total line below the two binds and press Run: the value stays 25 and only the step count changes. A model sees only text, never timing, and here every dependency is a named variable in the text, so it can reason about the values on the page and not about an interleaving it cannot observe.

Runs
lazy mu share(n: i64) -> i64 {
    n => 100 / n
}

mu only_what_is_read() -> i64 {
    _ => {
        let a = spawn share(4);
        let b = spawn share(0);
        a
    }
}
Lazy computation

Work happens only when its result is needed

only_what_is_read spawns share(4) and share(0) but returns only a, so it gives 100 / 4 = 25. share is declared lazy mu, so a call runs its body only when something reads its variable: nothing reads b, so 100 / 0 never runs, and spawn has no say in that, because the declaration settles it. Change a to a + b and press Run: now b is read, share(0) runs and the program crashes with DivideByZero, which a plain mu share would do even with b unread. Laziness is written once on the declaration, never at the call, so the model can tell from the text which work runs and which waits until it is read, without simulating an evaluation order it cannot observe.

The honest picture: most functions in munu’s source have a single case, and multi-case tables like those above are the minority. The short examples on this page (passed-along state, the table, deep patterns, mu and nu, familiar forms, a copied value, the joined names, the spawned consumer and the lazy calls) are written for it; the others are from munu’s source. The fit with a transformer is a design rationale and a likeness of shape only: munu does not compile to attention, and we have not measured that it lowers error rates. Effects such as receiving a message happen through calls, not through syntax. In our own tests the language is not more compact than mainstream languages. Its advantage is structure, not size.

Contracts and supervision

Recovery is part of the program.

A contract is munu’s unit of work, supervision and security. How it recovers and how fast it must answer are written as mu-calculus formulas and constants in the code, so they sit in the text the model is writing, and the compiler turns them into checks.

module page_recovery

enum Failure { Wounded }
enum Report { Reading(u64), ChildFailed(u64, u64), ChildDone(u64) }

const REPORTS_BOUND = 8u64;
const BED = 1u64;
const ONE = 1u64;
cdf RESPONSE {
    dmax: 200ms,
    handup: 50ms,
    expected: [(10ms, 0.9), (50ms, 0.99), (200ms, 1.0)]
}

eager nu attend(id: u64, out: [Report].end) -> [u64] {
    id, out => {
        let _ = send(out, Report::Reading(id));
        crash Failure::Wounded
    }
}

pub contract Medic(id: u64, out: [Report].end) -> [u64]
    substrate { bytecode }
{ attend(id, out) }

eager nu collect(rs: [Report], left: u64) -> [u64] {
    _, 0u64 => [],
    [], _ => [],
    [r | rest], left => match r {
        Report::Reading(id) => [id | collect(rest, left - 1u64)]
    }
}
Supervision strategy

Recovery is written beside the code, so the build can check it

Ward absorbs its medic’s failure in do:, but its must: is true, so it promises no response time, and a contract that answers a child’s failure on a port has to state one: the build refuses it, points at the must: line and says what to add. A model can act on that message directly. Press Check, change the must: line to must: nu X. [fail(!self, _)]~deadline(RESPONSE) X, and press Check again; RESPONSE is a cdf with several points, not a single number: 90% of answers within 10ms, 99% within 50ms, and every one within 200ms. Because the recovery rule and its deadline sit in the contract header, in the same text as the code they govern, the model writes them together instead of in separate settings or retry wrappers elsewhere, and the build checks them before the bot runs. Written for this page.

Runs
enum Failure { Lost, Wounded }
enum Report { Reading(u64), ChildFailed(u64, u64), ChildDone(u64) }

const REPORTS_BOUND = 8u64;
const ALPHA = 1u64;
const BRAVO = 2u64;
cdf RESPONSE {
    dmax: 200ms,
    handup: 50ms,
    expected: [(10ms, 0.9), (50ms, 0.99), (200ms, 1.0)]
}

eager nu drill(id: u64, out: [Report].end) -> [u64] {
    id, out when id == ALPHA => {
        let _ = send(out, Report::Reading(id));
        crash Failure::Lost
    },
    id, out => {
        let _ = send(out, Report::Reading(id));
        crash Failure::Wounded
    }
}

pub contract Corporal(id: u64, out: [Report].end) -> [u64]
    substrate { bytecode }
{ drill(id, out) }

eager nu command(rs: [Report]) -> [u64] {
    [] => [],
    [r | rest] => match r {
        Report::Reading(id) => [id | command(rest)]
    }
}

pub contract Major() -> [u64]
    substrate { bytecode }
    behaviour {
        do: nu X. [fail(alpha, Failure::Lost)] <restart(alpha)> X
                  and [fail(bravo, Failure::Wounded)] <absorb(bravo)> X
                  and [_] X
        must: nu X. [fail(!self, _)]~deadline(RESPONSE) X
    }
    children { alpha: Corporal, bravo: Corporal }
    ports {
        reports: [Report] {
            ends: a, b
            bound: REPORTS_BOUND
            do: nu X. [_] X
            must: true
        }
    }
{
    let self.alpha = spawn Corporal(ALPHA, reports.a);
    let self.bravo = spawn Corporal(BRAVO, reports.b);
    command(reports)
}

Supervision tree

A major restarts one corporal and absorbs the other’s failure

Major starts two corporals, alpha and bravo; each sends one reading and crashes, and Major’s do: answers each by its own rule, restart(alpha) for Failure::Lost and absorb(bravo) for Failure::Wounded, so the readings begin 1, 2 and then keep giving 1 as alpha restarts, until the step limit on this page stops the run. Each rule is one line, a failure on the left and its answer on the right, the same repeating shape as the cases of a function, so the model continues it row by row with the failure’s name in the text to match. The must: line holds Major to RESPONSE, a deadline given as several points, and spawn only binds each position: when the work runs is settled by drill, an eager nu, and munu is deterministic, so the same readings come out on every run. Written for this page.

Typed failures

A failure has a name and a type

first_object crashes with FetchFailure::EndedWithoutObject when the stream ends before an object arrives. A failure is a declared type and crash carries it to the supervisor, so recovery rules match on the cause, not on a log line. For a model that works from text, a declared name is a precise token to match on, where free-form message text would have to be interpreted.

Ports

The only place order can vary.

Every other value in munu has a single writer. Where several senders must feed one stream, you declare a port and say which orders it accepts, so the one place order can vary is written in the text.

Runs
pub contract SensorHub() -> [u64]
    substrate { bytecode }
    behaviour { do: nu X. [_] X  must: true }
    children { controller: Source, left: Source, right: Source }
    ports {
        readings: [Reading] {
            ends: ctl, lhs, rhs
            bound: READINGS_BOUND
            do:
                [from(lhs)] false
                and [from(rhs)] false
                and [from(ctl)] nu X. [_] X
            must:
                <from(ctl)>~deadline(CONFIG_MUST) true
                and nu X. [_]~deadline(SAMPLE_MUST) X
        }
    }
{
    let self.right      = spawn Source(RIGHT_CHANNEL, readings.rhs);
    let self.left       = spawn Source(LEFT_CHANNEL, readings.lhs);
    let self.controller = spawn Source(CONTROL_CHANNEL, readings.ctl);
    take(readings, COUNT)
}

module page_ports

const READINGS_BOUND = 8u64;
const LEFT_CHANNEL = 1u64;
const RIGHT_CHANNEL = 2u64;
const CONTROL_CHANNEL = 0u64;
const COUNT = 3u64;

cdf CONFIG_MUST {
    dmax: 20ms,
    handup: 5ms,
    expected: [(1ms, 0.9), (5ms, 0.99), (20ms, 1.0)]
}
cdf SAMPLE_MUST {
    dmax: 200ms,
    handup: 50ms,
    expected: [(10ms, 0.9), (50ms, 0.99), (200ms, 1.0)]
}

struct Reading { channel: u64, value: u64 }

nu idle(r: Reading) -> [Reading] {
    r => [r | idle(r)]
}

eager nu speak(channel: u64, out: [Reading].end) -> [Reading] {
    channel, out => {
        let r = Reading { channel: channel, value: channel };
        let _ = send(out, r);
        [r | idle(r)]
    }
}

pub contract Source(channel: u64, out: [Reading].end) -> [Reading]
    substrate { bytecode }
{ speak(channel, out) }

eager nu take(rs: [Reading], left: u64) -> [u64] {
    _, 0u64 => [],
    [], _ => [],
    [r | rest], left => [r.channel | take(rest, left - 1u64)]
}
Ports

The only place non-determinism can enter

SensorHub starts three sources that feed one port, readings. Its formula says neither sensor may speak until the controller has, after which anything goes, and CONFIG_MUST and SAMPLE_MUST, each a cdf with several points, say how soon the controller and then each reading must arrive. Press Run: the controller, started last, comes first, as the formula requires, then come 2 and 1 in an order the contract leaves open, and moving a spawn line can change it; the stream never ends, so take stops after COUNT readings. Every other value in munu has one writer, so a failure that depends on ordering can only be here, and a transformer, which sees text and never timing or interleaving, is told in the contract where to look and which rule to tighten. Written for this page.

ψ-terms

Shared work, filled in by many.

munu’s types are ψ-terms (psi-terms): structures that can be partly known. Each party adds what it knows, and the store checks it against what everyone else said.

Shows a compile error

mu g(r: {a: bool}) -> u64 { r => 0u64 }
mu main() -> u64 { _ => { let y; let z = 1u64; let r = {a: y}; f(r); g(r) } }
Type-checks

ψ-terms

Shared work that several parties fill in

In the first compiler test, let y; leaves a field blank in {a: y}; f expects a number there and g a true-or-false value, so the program is refused with an error that the variable keeps one type. In the second, a later assignment fills the blank. A model writes left to right and often does not yet know every field, so a blank lets it leave the field open and fill it in later instead of inventing a placeholder, and when several parties each add what they know, a conflict is reported as a message to act on, not overwritten.

Dataflow and scenes

Variables that are filled once, and screens that are data.

A munu variable starts empty, is filled in once and is never changed. Anything that needs it waits until it has a value. Apps use the same rule for input, and draw themselves as scene values.

Scenes

A screen is a value

button_face returns a scene: a styled layout with a fill colour and padding around the label’s text, built by ordinary mu functions, and nothing is painted until munuScene reads the tree. A screen that is a value is text a model can read and write, which a screen of pixels is not, and munuScene is designed to hand the same tree to the agent so it can act on it without a screenshot.

Dataflow

Wait for a value to be bound

click_cycle returns the current scene, then waits on click, a variable with no value yet that the button fills in once; the next step continues only when it has one. There are no callbacks or handlers to register. A model sees only text, so a wait that is one named variable in the code, with the button wired to it beside it, is a dependency it can read directly instead of tracing to a handler elsewhere.

Facts and history

Memory you can question later.

Long-term memory is a set of typed facts, changed only in transactions and queried as of any moment.

Type-checks
pub relation Module { name: string @key, path: string, lines: i64 }

pub transaction add_module(name: string, path: string, lines: i64) -> () {
    name, path, lines => {
        assert Module { name: name, path: path, lines: lines };
    }
}
Facts

Memory is a set of typed facts

Module is a relation with a key and typed fields, and memory is changed only through transactions like add_module, which assert a fact. The compiler stops a query from calling a transaction, so reading memory can never change it. The keyword that opens each piece of code, query or transaction, tells a model from the text whether it can change memory, and a mix-up is rejected with a message it can read.

Hyperbolic routing

A network with no central directory.

The routing code is written in munu and runs today between separate node processes in our tests, with every message sealed in an encrypted frame. Joining every munuOS machine and every bot, reachable by its QR code, is still ahead.

The shape of the network

Records in the middle

IP moves packets to places, and named-data networking moves data by name. munu moves structured data that is still being worked out, so ψ-terms (psi-terms) sit in the middle. You can send a record before you know all of it, and anyone reading a field that is missing just waits until someone fills it in. A reader asks and the owner tells; nothing is pushed unasked.

Every field has exactly one writer. If a node tells something that contradicts what is already there, that thread is refused and fails, and the data stays as it was. Once a record is sealed it gets a hash, and anyone holding it can serve it, not only whoever made it.

Underneath, each node has a place on the hyperbolic map and forwards by distance, and every message travels in a fixed-size BlackFrame, sealed end to end and again hop by hop with X25519 and ChaCha20-Poly1305, so a forwarder sees only where a frame is going.

Built and tested between node processes: the routing, the frames, refused contradictions, waiting readers and serving by hash. Still ahead: sending partial records over the wire (closed values and streams cross today), and linking munuOS machines.

mu hyperbolic_distance(r1: f64, a1: f64, r2: f64, a2: f64) -> f64 {
    r1, a1, r2, a2 => {
        let x1 = f64_mul(r1, f64_cos(a1));
        let y1 = f64_mul(r1, f64_sin(a1));
        let x2 = f64_mul(r2, f64_cos(a2));
        let y2 = f64_mul(r2, f64_sin(a2));
        let dx = f64_sub(x1, x2);
        let dy = f64_sub(y1, y2);
        let delta_sq = f64_add(f64_mul(dx, dx), f64_mul(dy, dy));
        let d1sq = f64_sub(1.0, f64_mul(r1, r1));
        let d2sq = f64_sub(1.0, f64_mul(r2, r2));
        let denom = f64_mul(d1sq, d2sq);
        f64_acosh(f64_add(1.0, f64_div(f64_mul(2.0, delta_sq), denom)))
    }
}
Hyperbolic routing

Every node has a place on a curved map

hyperbolic_distance measures how far apart two nodes are in the Poincaré disk, each given as a radius and an angle; a packet goes to the neighbour closest to its destination by this measure, so a node needs to know only its neighbours. The body names every intermediate value on its own line, x1, dx, delta_sq, denom, and each is bound once. So each line is written from names directly above it, a nearby, explicit dependency of the kind a transformer works from.

Architecture

Three parts, one language.

How AbideBot is put together around munu. Parts marked planned or in development are designs, not shipped software.

munuOS In development

The always-on operating system the agent lives in: a minimal Linux-based operating system image where munu is the first process, one per customer. It includes the munu compiler. It is designed so the agent writes a module, compiles it on munuOS and swaps it in, with supervision restarting a failed part by its rule and a bad version rolling back.

munuScene In development

The AI-native browser and desktop app. It draws scenes, not HTML, and turns what you press and type into values bound to the variables the app is waiting on. The agent runs on munuOS, not in munuScene, and is designed to use the same scenes as you do.

The network In development

Shared state as ψ-terms in one store, designed so tells commute and only the new part of a value travels. Routed by hyperbolic coordinates, with every message sealed in an encrypted BlackFrame. The routing and the frames are built and tested between nodes; running it between munuOS machines is planned. Sites, documents and apps are designed to live here, not on the public web.

The honest picture: the compiler, the code shown above, the routing and encrypted frames between test nodes, and munuOS’s first stages exist. The agent’s direct use of apps in munuScene, the network between munuOS machines, self-hosting and published docs are planned. We will not claim savings or uptime before we can measure them.
