Why AbideBot

Designed to keep running, and to tell you when it isn't.

Most AI assistants are chat apps with a server bolted on. AbideBot runs on its own purpose-built runtime, designed so agents can do operational work without surprises.

Response-time guarantees you can measure

Declare how fast each agent must respond. Every run is measured against that guarantee, and a miss is detected and reported, not discovered in a postmortem.

Alerts where your on-call already lives

A missed guarantee, a failed step or a crashed routine goes to Slack or PagerDuty with its cause attached.

An always-on node of your own

Each customer gets a separate virtual machine. Customers never share a machine or its core. Your agents keep working when your laptop is closed.

Sealed and locked down

The node runs AbideBot and nothing else. There is no shell and no way to start other programs, and the kernel ships hardened. You can check the image fingerprint against the public release.

Supervised, with automatic rollback

Every component is supervised, and a crash stays inside its boundary. A new routine version runs on probation, and the previous one returns automatically if it fails.

An audit trail you can hand to compliance

Changes are signed and versioned, permissions carry a signed record of where they came from, and the audit log can be exported.

Model-native by design

A language shaped like the model that writes it.

The AbideBot runtime language was designed so that a language model can read and write it the way it reads everything else: left to right, from the text in front of it, with nothing hidden.

How the language is written
Why it suits a transformer
no mutationNo hidden state

Values never change after they are bound. There is no assignment statement, no mutable variable and no compound update. An update builds a new value, and long-running state is passed along explicitly as an input.

→
Nothing to simulate

A model does not have to track a variable changing over time in its head. What a function means can be read straight off the text in front of it.

table of casesEvery function is a table

A function body is always a list of cases: an input pattern on the left, its result on the right, with a fixed separator between them and each case on its own line.

→
Tables are easy to read and continue

Left-maps-to-right rows are one of the most regular patterns in text. Each new case follows the shape of the one above it.

finite vs ongoingLeast and greatest fixed points look different

Finite, inductive computations and never-ending, coinductive processes are declared with different keywords. A finite recursive one must state why it stops. An ongoing one must keep producing output.

→
Told apart from the first word

A model knows from the first token whether it is writing something that terminates or a stream that runs forever, and the compiler checks the matching rule for each.

familiar formsBuilt from syntax that is already common

Braces, typed parameters, return arrows, match cases, structs, imports and list patterns follow forms that are already common in public code.

→
Patterns seen countless times

Models have seen these shapes countless times in public code, and the common keywords and operators are single tokens in widely used tokenizers. The few new constructs are where the compiler checks hardest.

typed holeThe gap is a typed blank

When a decision is handed to the model, the known facts are laid out as typed entries in a fixed order and the unknown is the same entry with its value left blank.

→
Fill-in-the-blank completion

The model attends to the known values and produces the one value that fills the gap. The declared type keeps the answer in shape.

signature firstRules come before the body

Input types, the return type, preconditions, guarantees and the stopping rule are all written before the code, in a fixed order.

→
Constraints are read first

A model writes left to right. By the time it reaches the body it has already read every constraint the body must meet.

no hidden jumpsNo hidden control flow

There are no loops, early returns, breaks or exceptions. Repetition is recursion, branching is a case table, and the compiler checks that every case is covered.

→
Every path is on the page

What the model reads is all that can happen. There is no jump elsewhere in the file that changes the meaning of a line.

Meet Dude

Your agent is called Dude. Rename it if you like.

Every new agent starts out as Dude. Call yours triage, payments-watch or anything else. Whatever its name, it writes real programs for your tasks and checks them before they go live.

  • Compiled, not improvised. The agent writes a routine and compiles it on your node. Compile errors go straight back to the agent, and it fixes them.
  • Calls the AI only when it needs judgement. The routine itself runs as checked code, so the AI is not consulted on every step.
  • Approvals only a human can give. Risky steps pause until someone on your team approves them. The agent cannot answer for you.
  • A factory reset that always works. A protected core can boot with only the essentials, so a bad change can never lock you out.

How it works

A node, a desktop app, and one shared record

The node does the work, the native desktop app is where your team talks to it, and both share one store of facts.

Choose where it runs

A hosted node with us, or the same sealed image on your own infrastructure. Hong Kong data residency is planned for Business SLA nodes.

Describe the job

Ask in plain language in a room or thread. Set triggers by time or by event, and set the response time you need.

It runs, measured

The agent builds the routine and runs it on probation. Every run is measured against its guarantee, and misses go to your alert channel.

Review and audit

Status shows what is working and what is waiting for you. Only changes sync between devices, and the audit log can be exported.

FAQ

Questions, answered calmly

Who is AbideBot for?

Platform, SRE and ops teams, mainly in Hong Kong and Asia, who want AI agents that run continuously and behave predictably: triage, checks, reports and other routine operational work.

What does "response-time guarantee" mean here?

You declare how quickly an agent must respond. AbideBot measures every run against that, detects a miss and alerts you. It is a guarantee you set and monitor for your own agents, not a contractual service level. Contractual SLAs are planned only for the Business SLA node.

Is there an uptime SLA?

Not yet. The Team node is designed for a 99.5% uptime target, shown on a public status page, with no service credits. A 99.9% monthly SLA with service credits is planned for the Business SLA node, which is coming later.

Is my node shared with other customers?

No. Each customer gets a separate virtual machine. Customers never share a machine or its core.

Where is my data stored?

Hong Kong data residency is planned for the Business SLA node. If you need full control, you can run the same sealed image on your own infrastructure, with annual support available.

Can agents see all our files?

No. They can read and write only inside the folders you grant, one at a time, and you can revoke a grant at any time. The app tells you when granted files go to a hosted node and to the AI model provider. Code written by the AI never runs on your own computer with your computer's permissions.

How is AI usage billed?

Through a prepaid balance that you top up by hand or automatically. It is charged at the model provider's cost plus a small disclosed markup. When the balance reaches zero, the AI stops. Nothing is billed after the fact.

Why is my agent called Dude?

It is the default name. Rename it whenever you like.

When can we start?

A private beta is planned for around February 2027 and paid plans for around May 2027. Dates may move. Join the waitlist and we will email you.
