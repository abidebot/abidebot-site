Features

Everything AbideBot is built to do.

AbideBot is in development and not yet available. This page describes the product we are building. A private beta is planned for around February 2027. Join the waitlist to be first in.

Your always-on node

A dedicated, locked-down virtual machine for every customer.

One machine per customer

Each paying customer gets a separate virtual machine. Customers never share a machine or its core.

Always on

Team and Business nodes stay up between jobs. Your routines keep running whether or not anyone has the app open.

Nothing else runs on it

No shell, no extra programs. A filter set at start-up blocks every attempt to launch another program, and this is checked on every boot.

Hardened kernel

Address randomisation, stack protection, memory zeroing and CPU mitigations are on. Risky kernel interfaces are switched off, and the build checks each one.

Verifiable sealed image

Reproducible builds. The app shows the fingerprint of the image on your node so you can compare it with the public release.

Fast, light start-up

Lean enough that, in our early tests on Apple silicon, it went from cold start through a secure web request to shutdown in under a second.

Sleeps when idle, wakes on time

A Developer box sleeps from a snapshot when idle and wakes before its next scheduled routine.

Secure connections built in

Modern encrypted connections (TLS 1.3) with standard certificate checks, built into the core.

Credentials stay in custody

Secrets and permissions live in a protected core. They are never baked into the downloadable image.

Hosted or self-hosted

Use a node we host, or run the same sealed image on your own infrastructure with one launcher. Images for x86_64 and arm64.

Agents that behave

Your agent (called Dude until you rename it) writes real programs, and a protected core keeps them honest.

Name it what you like

Every new agent is called Dude by default. Rename it to suit the job.

Writes real code for your tasks

The agent turns your request into a program and compiles it on your node, rather than improvising in chat.

Errors it can read and fix

Compile errors go back to the agent as the result of its turn, written so an AI can act on them.

Probation and automatic rollback

A new version runs under supervision first. If it crashes, the previous version returns, the agent learns why, and your alert channel hears about it.

Changes that survive a reboot

Approved versions are recorded and kept across restarts. A factory boot ignores them and loads only the protected core.

A core it cannot change

Start-up, credential custody, your spending limits and the safety checks sit in a fixed core. The agent can improve its routines, never its own guard rails.

Hard spending limits

Your AI spending limits are held as a protected permission. The agent cannot raise them.

Least-privilege sessions

The agent can name and touch only what it has been explicitly granted. Nothing else is reachable.

Honest state

If a step is refused, the earlier steps stand and the agent sees the true result and the reason. Nothing is hidden from it or from you.

AI only when it is needed

A routine runs as compiled code and calls the AI only when it needs judgement, not on every step.

Move a routine to the node

Start a routine on your own machine and move it to your node. It is the same routine in both places.

The desktop app

A fast native app where your team talks to its agents, approves actions and reviews work.

Native, not a web wrapper

A true desktop application, with no embedded browser runtime.

Rooms, bots and threads

Organise work into rooms with one or more assistants, threads, questions and attachments.

Live status

See at a glance when an agent is working and when it is waiting for you.

Approvals only a human can answer

A question that only a person may answer pauses the agent until someone responds.

Grants instead of settings

Permissions are grants you hand out. Revoke one and the work that depended on it stops immediately.

Folder-by-folder file access

Read, list and write only inside folders you grant, with notifications. The app tells you when files leave your machine.

Works with an offline laptop

When your machine is offline, reads from it wait with a deadline, and you are told if a wait runs too long.

Everything is a tab

Conversations and applications sit side by side as equal tabs.

Build together

You and the agent edit the same source, with errors shown right beside it.

Inspectable layout

Where everything is on screen is available as data, so tests, agents and accessibility tools can ask where a thing is.

Under the hood

Our own purpose-built runtime, designed for agents that have to stay up.

Contracts on every component

Each component carries a machine-checked contract that states what it must do, checked when the code is compiled.

Response-time guarantees in the code

Deadlines and response-time guarantees are part of each component. A miss is detected and reported, not discovered later.

Supervision trees

Every component is supervised. A crash stays inside its boundary, and a supervisor decides to restart, recover or escalate.

Lock-free by construction

Shared state is written once and read by anyone who waits for it. Updates combine in any order, so parties never block each other.

One shared store across devices

Your desktop app and your cloud computer share one store of facts. Only the changes travel over the wire.

Capability security

Access is a token that can be granted, narrowed, split and revoked, with a signed chain showing where it came from. User code gets no direct system access.

Failures carry their cause

When something fails, the reason travels with it, so the agent and you know why.

Arithmetic you can trust

Every calculation fits its type or stops with a clear error. Nothing silently wraps around.

Signed, versioned updates

Code versions are content-addressed and signed, and each new version links to the one before. Updates swap in while running.

Queryable long-term memory

A content-addressed fact database with a query engine keeps structured, auditable records.

Delete means deleted

Private records can be encrypted with their own keys, so destroying a key erases the record.

Location-transparent

The same code runs on one machine or across many. Anything can be found by its address, wherever it lives.

Memory checked before launch

Each component declares its memory needs up front, and a deployment that would not fit is refused before it starts.

Small, audited core

A deliberately small trusted core, with unsafe code confined to one audited place and the inner loop designed for mechanical verification.

Formally specified

The core behaviour is written as a formal model in a proof assistant, and that model is the authoritative specification.

One vetted cryptography library

A single audited cryptography library is the only one allowed, enforced at the core.
