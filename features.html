Features

Your always-on node

A dedicated, locked-down virtual machine for every customer.

One machine per customer

Each paying customer gets a separate virtual machine. Customers never share a machine or its core.

Always on

Team and Business nodes stay up between jobs. Your routines keep running whether or not anyone has the app open.

Nothing else runs on it

No shell, no extra programs. A filter set at start-up blocks every attempt to launch another program, and this is checked on every boot.

Hardened kernel

Address randomisation, stack protection, memory zeroing and CPU mitigations are on. Risky kernel interfaces are switched off, and the build checks each one.

Verifiable sealed image

Reproducible builds. The app shows the fingerprint of the image on your node so you can compare it with the public release.

Fast, light start-up

Lean enough that, in our early tests on Apple silicon, it went from cold start through a secure web request to shutdown in under a second.

Sleeps when idle, wakes on time

A Developer box sleeps from a snapshot when idle and wakes before its next scheduled routine.

Secure connections built in

Modern encrypted connections (TLS 1.3) with standard certificate checks, built into the core.

Credentials stay in custody

Secrets and permissions live in a protected core. They are never baked into the downloadable image.

Hosted or self-hosted

Use a node we host, or run the same sealed image on your own infrastructure with one launcher. Images for x86_64 and arm64.

Agents that behave

Your agent (called Dude until you rename it) writes real programs, and a protected core keeps them honest.

Name it what you like

Every new agent is called Dude by default. Rename it to suit the job.

Writes real code for your tasks

The agent turns your request into a program and compiles it on your node, rather than improvising in chat.

Errors it can read and fix

Compile errors go back to the agent as the result of its turn, written so an AI can act on them.

Probation and automatic rollback

A new version runs under supervision first. If it crashes, the previous version returns, the agent learns why, and your alert channel hears about it.

Changes that survive a reboot

Approved versions are recorded and kept across restarts. A factory boot ignores them and loads only the protected core.

A core it cannot change

Start-up, credential custody, your spending limits and the safety checks sit in a fixed core. The agent can improve its routines, never its own guard rails.

Hard spending limits

Your AI spending limits are held as a protected permission. The agent cannot raise them.

Least-privilege sessions

The agent can name and touch only what it has been explicitly granted. Nothing else is reachable.

Honest state

If a step is refused, the earlier steps stand and the agent sees the true result and the reason. Nothing is hidden from it or from you.

AI only when it is needed

A routine runs as compiled code and calls the AI only when it needs judgement, not on every step.

Move a routine to the node

Start a routine on your own machine and move it to your node. It is the same routine in both places.

The desktop app

A fast native app where your team talks to its agents, approves actions and reviews work.

Native, not a web wrapper

A true desktop application, with no embedded browser runtime.

Rooms, bots and threads

Organise work into rooms with one or more assistants, threads, questions and attachments.

Live status

See at a glance when an agent is working and when it is waiting for you.

Approvals only a human can answer

Grants instead of settings

Permissions are grants you hand out. Revoke one and the work that depended on it stops immediately.

Folder-by-folder file access

Read, list and write only inside folders you grant, with notifications. The app tells you when files leave your machine.

Works with an offline laptop

When your machine is offline, reads from it wait with a deadline, and you are told if a wait runs too long.

Everything is a tab

Conversations and applications sit side by side as equal tabs.

Build together

You and the agent edit the same source, with errors shown right beside it.

Inspectable layout

Where everything is on screen is available as data, so tests, agents and accessibility tools can ask where a thing is.

Model-native by design

The language was designed so that a transformer can read and write it the way it reads everything else: left to right, from the text in front of it, with nothing hidden. The first three rows are the heart of the design. These are design properties, not measured results.

How the language is written
Why it suits a transformer
no mutationNo hidden state

Values never change after they are bound. There is no assignment statement, no mutable variable and no compound update. An update builds a new value, and long-running state is passed along explicitly as an input.

→
Nothing to simulate

A model does not have to track a variable changing over time in its head. What a function means can be read straight off the text in front of it.

table of casesEvery function is a table

A function body is always a list of cases: an input pattern on the left, its result on the right, with a fixed separator between them and each case on its own line.

→
Tables are easy to read and continue

Left-maps-to-right rows are one of the most regular patterns in text. Each new case follows the shape of the one above it.

finite vs ongoingLeast and greatest fixed points look different

Finite, inductive computations and never-ending, coinductive processes are declared with different keywords. A finite recursive one must state why it stops. An ongoing one must keep producing output.

→
Told apart from the first word

A model knows from the first token whether it is writing something that terminates or a stream that runs forever, and the compiler checks the matching rule for each.

familiar formsBuilt from syntax that is already common

Braces, typed parameters, return arrows, match cases, structs, imports and list patterns follow forms that are already common in public code.

→
Patterns seen countless times

Models have seen these shapes countless times in public code, and the common keywords and operators are single tokens in widely used tokenizers. The few new constructs are where the compiler checks hardest.

typed holeThe gap is a typed blank

When a decision is handed to the model, the known facts are laid out as typed entries in a fixed order and the unknown is the same entry with its value left blank.

→
Fill-in-the-blank completion

The model attends to the known values and produces the one value that fills the gap. The declared type keeps the answer in shape.

signature firstRules come before the body

Input types, the return type, preconditions, guarantees and the stopping rule are all written before the code, in a fixed order.

→
Constraints are read first

A model writes left to right. By the time it reaches the body it has already read every constraint the body must meet.

no hidden jumpsNo hidden control flow

There are no loops, early returns, breaks or exceptions. Repetition is recursion, branching is a case table, and the compiler checks that every case is covered.

→
Every path is on the page

What the model reads is all that can happen. There is no jump elsewhere in the file that changes the meaning of a line.

bracketsBrackets, not indentation

Blocks open and close with explicit brackets, and spacing carries no meaning.

→
No counting spaces

Where a block ends never depends on how many spaces a line starts with.

one layoutOne canonical layout

Programs have a single printed form: one meaning, one text.

→
Fewer equivalent spellings

There are fewer ways to write the same thing, so there is less to choose between at each step.

keyword-ledThe first word says what follows

Every declaration starts with its own keyword, and the parser decides what comes next from the next token or two.

→
Grammar-guided output

Small lookahead suits decoding that is guided by the grammar.

names carry kindCapitalisation is enforced

Type and component names are capitalised, constants are upper case and functions are lower case, all checked by the compiler.

→
Kind visible at a glance

The first characters of a name tell the model what kind of thing it refers to.

local namesInputs restated case by case

Each case names its inputs again, so the names a line uses are usually just above it.

→
Short look-back

The values a line depends on sit close to it in the text.

error at the openingErrors point where a block opened

An unclosed block is reported at the place it opened, not just at the end of the file.

→
Repairs land on the right line

A model fixing its own code is pointed at the actual mistake.

The honest trade-off: a new language is one no model has seen in training. The design leans on familiar syntax, a strict compiler, the fixed layout and the typed blanks to make up for that. In our own tests the language is not more compact than mainstream languages. Its advantage is structure, not size.

The runtime fits the model too

Conversations keep their cache

A conversation is an ongoing stream of turns that keeps its session, so the cached context stays warm between turns and can be saved and restored after a restart.

Sessions you can edit

A model session can be extended, rolled back, branched and stored, like an editable prefix.

Waiting is reading a blank

A step starts a model call and waits on a value that is filled when the result is ready. Other agents keep running.

Token controls built in

Token counts, stop sequences, per-token probabilities and reasoning-depth settings are available to the program.

Built for a model that writes the code

Mistakes surface immediately

If the model calls a function or tool that does not exist, the compiler rejects it or the runtime fails to resolve it. Each typed unknown is checked on its own, so errors do not compound.

Errors written for a model to read

When code the model wrote crashes, the failure comes back as the result of its turn, so it can read it and fix the code. Crash reasons name the actual resource at fault, so a model reading them is not sent the wrong way.

One bounded attempt per repair

A repair gets one attempt with a time budget, contained in its own supervised box. Runaway retry loops are ruled out by construction.

Fewer calls over time

One call can produce a program with gaps in it. The program fills the routine gaps itself and calls the model only for genuinely new decisions.

Local or remote, same code

A model session is reached through a capability, so the same code works whether the model runs on this machine or on a GPU server.

Under the hood

Our own purpose-built runtime, designed for agents that have to stay up.

Contracts on every component

Each component carries a machine-checked contract that states what it must do, checked when the code is compiled.

Response-time guarantees in the code

Deadlines and response-time guarantees are part of each component. A miss is detected and reported, not discovered later.

Supervision trees

Every component is supervised. A crash stays inside its boundary, and a supervisor decides to restart, recover or escalate.

Lock-free by construction

Shared state is written once and read by anyone who waits for it. Updates combine in any order, so parties never block each other.

One shared store across devices

Your desktop app and your cloud computer share one store of facts. Only the changes travel over the wire.

Capability security

Access is a token that can be granted, narrowed, split and revoked, with a signed chain showing where it came from. User code gets no direct system access.

Failures carry their cause

When something fails, the reason travels with it, so the agent and you know why.

Arithmetic you can trust

Every calculation fits its type or stops with a clear error. Nothing silently wraps around.

Signed, versioned updates

Code versions are content-addressed and signed, and each new version links to the one before. Updates swap in while running.

Queryable long-term memory

A content-addressed fact database with a query engine keeps structured, auditable records.

Delete means deleted

Private records can be encrypted with their own keys, so destroying a key erases the record.

Location-transparent

The same code runs on one machine or across many. Anything can be found by its address, wherever it lives.

Memory checked before launch

Each component declares its memory needs up front, and a deployment that would not fit is refused before it starts.

Small, audited core

A deliberately small trusted core, with unsafe code confined to one audited place and the inner loop designed for mechanical verification.

Formally specified

The core behaviour is written as a formal model in a proof assistant, and that model is the authoritative specification.

One vetted cryptography library

A single audited cryptography library is the only one allowed, enforced at the core.
